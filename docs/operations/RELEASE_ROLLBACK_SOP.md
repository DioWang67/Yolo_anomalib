# Release And Rollback SOP

This SOP defines how to promote and roll back runtime, model, and config
artifacts. The goal is traceability over clever automation.

## Release Unit

A production or pilot release is not just an exe. Treat these as one release
unit:

- application bundle: `dist\yolo11_inference\`
- root config: `config.yaml`
- product configs: `models\<product>\<area>\<type>\config.yaml`
- model weights or exported runtime artifacts
- runtime manifest generated by the package process
- readiness report JSON
- pilot acceptance summary, when applicable

Do not promote a model without promoting the config that was validated with it.

## Version Naming

Use a release folder name that includes date, product, area and intent:

```text
releases\
  2026-07-08_PCBA1_A_pilot\
```

Recommended model artifact naming is defined in `docs/model_lifecycle/MODEL_VERSION_GUIDE.md`.
When existing products still use `best.pt`, keep a checksum and copy of the
validated file in the release folder until the product is migrated to versioned
weights.

## Release Checklist

1. Confirm working tree scope.
2. Build or receive runtime bundle.
3. Copy the exact model/config pair into the release folder.
4. Run readiness gate.
5. Run smoke inference on golden board images.
6. Run known NG validation.
7. Save review manifest and pilot summary for PCBA pilot.
8. Record checksums.
9. Tag or document the source commit.
10. Store rollback target from the previous accepted release.

## Build Runtime

```powershell
build_exe.bat
```

Output:

```text
dist\yolo11_inference\
```

The packaged executable is built from `GUI.py`. Packaged diagnostics:

```powershell
.\yolo11_inference.exe --check-hikrobot-runtime
.\yolo11_inference.exe --check-camera-grab
```

## Validate Config

```powershell
D:\miniconda\envs\yolo_anomalib\python.exe tools\production_readiness_check.py `
  --config models\<PRODUCT>\<AREA>\yolo\config.yaml `
  --product <PRODUCT> `
  --area <AREA> `
  --output-json readiness_report_<PRODUCT>_<AREA>.json
```

Rules:

- `FAIL`: block release.
- `WARN`: allowed only for supervised pilot with a written engineering note.
- Missing weights or expected boxes are release blockers for PCBA inspection.

## Record Checksums

Use PowerShell:

```powershell
Get-FileHash .\yolo11_inference.exe -Algorithm SHA256
Get-FileHash .\models\<PRODUCT>\<AREA>\yolo\config.yaml -Algorithm SHA256
Get-FileHash .\models\<PRODUCT>\<AREA>\yolo\weights\best.pt -Algorithm SHA256
```

If the model is an OpenVINO directory, hash all files in the directory and keep
the output with the release record.

## Promote Release

1. Stop the running inspection app.
2. Copy the current deployment folder to a rollback location.
3. Copy the new release folder onto the inspection PC.
4. Run packaged runtime preflight.
5. Run camera grab preflight.
6. Run golden board smoke test.
7. Start supervised pilot or production mode only after checks pass.

## Rollback Procedure

Rollback is required when:

- the app cannot start;
- runtime preflight fails;
- camera preflight fails on a machine that previously passed;
- golden board repeatability regresses;
- known NG samples no longer fail with expected reason codes;
- review manifest shows unacceptable false pass or false fail behavior.

Steps:

1. Stop the running app.
2. Move the failed deployment folder aside; do not delete it until logs are
   collected.
3. Restore the previous accepted release folder.
4. Run `--check-hikrobot-runtime`.
5. Run `--check-camera-grab` if camera mode is used.
6. Run one golden board smoke test.
7. Record rollback reason, failed release folder, restored release folder and
   operator impact.

## Trade-Off

This SOP intentionally avoids a heavy release platform. For the current project
scale, a complete release folder plus checksums and readiness reports gives
enough traceability without slowing down pilot iteration.

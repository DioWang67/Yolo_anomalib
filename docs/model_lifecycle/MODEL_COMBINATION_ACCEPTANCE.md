# 模型組合驗收與發布

本文件說明如何使用獨立驗收照片，測試 YOLO、顏色設定及未來 Anomalib
等檢測元件的組合。驗收工具只建立證據與候選發布版本，不會自動切換正式
檢測組合，也不會把照片送入訓練資料。

## 1. 三層版本概念

| 層級 | 用途 | 是否直接影響產線 |
| --- | --- | --- |
| 元件版本 | YOLO、Anomalib、完整顏色基準、逐色修訂 | 否 |
| 候選組合 | 將指定元件鎖定成可重現的完整檢測方案 | 否 |
| 正式組合 | 經工程人員具名啟用的原子發布版本 | 是 |

不要分別手動切換 YOLO 與顏色檔。正式切換以完整組合為單位，系統才可保存
每個元件的版本、checksum、驗收證據及回滾目標。

目前內建 Pipeline Template：

- `yolo_visual_v1`：YOLO，可選 Stats Color 與規則決策；
- `anomalib_visual_v1`：Anomalib，可選規則決策；
- `fusion_visual_v1`：YOLO＋Anomalib＋融合決策，可選 Stats Color。

新 detector 必須先登錄元件類型與相容的 Pipeline Template，不得以任意檔案
路徑繞過契約驗證。

## 2. 獨立驗收資料

從專案根目錄執行：

```powershell
.\start_model_acceptance.bat
```

選擇產品與工位後加入圖片，逐張確認實物真值為 OK 或 NG。系統自動維護
`acceptance/<product>/<area>/ground_truth.csv`，一般使用者不需要手寫 CSV。

驗收集必須遵守：

1. 驗收照片不可複製進訓練、validation 或 test dataset。
2. 模型重跑只更新機器判定；人工真值不會被覆寫，也不必重新標記。
3. 每次正式比較前建立不可變快照及異機備份。
4. 建議先以 50–100 張做 smoke test，再累積到至少 300 張。
5. 每個重要 NG 原因至少收集 5–10 張；沒有該類 NG 時必須標示未知，
   不得填成 0%。

`acceptance/`、`acceptance_reports/`、顏色候選及發布指標都是站點資料，
不提交到原始碼 Git。備份 ZIP 需保存到另一個磁碟或受控伺服器。

## 3. 單一模型與組合測試

### 3.1 建立比較基準

1. 確認所有預計採用的照片已完成實物真值。
2. 使用目前正式模型執行全部推論。
3. 按`建立基準快照`。
4. 模型或設定改動後按`全部重新推論`。
5. 按`比較最新快照`查看改善、退步、誤殺與漏檢。

#### 每次推論綁定一組固定 artifact

按下任何推論按鈕時，系統會先把這次要用的權重、model config、global config、
顏色模型與逐色修訂鎖定成一組 artifact bundle，並為它計算一個內容雜湊。推論
開始與結束各驗證一次；期間有任何檔案被換掉，該次結果會被拒絕，而不是產生一份
指向已變更檔案的報告。

結果以**原子方式**提交：推論期間的結果先寫進 `acceptance/<product>/<area>/runs/`
底下該次 run 的目錄，全部完成後才一次寫入 manifest。中途失敗或取消不會改動原本
的正式結果，狀態列會明確顯示「原正式結果未變更」。

#### 局部推論與正式快照

`建立基準快照`要求 manifest 內每一筆結果都來自**同一組 artifact bundle**、
每個 run 都已 COMPLETED，且沒有待推論、ERROR 或真值異常的樣本。

這個條件是以 bundle 而非「單一次執行」為準，因此：

- `推論目前圖片`／`推論未完成圖片`在**相同組合**下重跑，不會丟棄其他樣本的
  結果。少數樣本因暫時性 I/O 失敗而 ERROR 時，只需重跑那幾張。
- 換成**不同組合**（不同權重或不同顏色模型）後執行局部推論，其餘樣本的結果
  必然失效，系統會先詢問並說明將清除幾張，人工真值不受影響。

因此累積一份完整可快照的 manifest，不再必須每次都按`全部重新推論`。

### 3.2 YOLO × 顏色組合

按`YOLO × 顏色組合測試`，勾選一個以上 YOLO 與顏色方案，再按
`開始組合測試`。每個勾選的 YOLO 都會與每個勾選的顏色設定配對，
並依序使用同一批已確認照片重新推論。

其中「目前正式」YOLO 使用工位當下實際生效的 `config.yaml`；歷史 YOLO
版本使用各自不可變的 config 快照。選取完整顏色方案時，完整顏色基準與該
方案綁定的逐色修訂會一併鎖定，不會再混入執行當下的 Active 修訂。因此主
視窗選取相同方案後執行「全部重新推論」，會與矩陣中的相同組合使用一致的
權重、runtime config、顏色基準及逐色修訂。

### 3.3 未列出的顏色設定

顏色清單中可能出現灰階、無法勾選的項目，並附上原因。這些是屬於本工位、
但系統判定不可納入比較的項目，列出而不隱藏，是為了避免你把「看不到」誤判成
資料遺失而重建一份其實還在的基準。原因分為三類：**演算法**、**量測條件**、
**檔案完整性**。

| 原因 | 說明 | 處理方式 |
| --- | --- | --- |
| `演算法 <舊版>（目前為 <新版>）` | 該基準由舊版重建演算法產生，裁切座標空間不同 | 需以現行演算法重新執行顏色基準重建 |
| `未記錄重建演算法（目前為 <新版>）` | 檔案本身沒有記錄產生它的演算法，無法確認取樣幾何相同 | 同上；訓練端直接輸出的顏色統計屬於此類 |
| `顏色 ROI policy 不一致（基準：…；執行期：…）` | 統計量是在另一組 `color_roi_policy` 下量到的 | 對齊工位設定，或以現行幾何重建基準 |
| `未記錄顏色 ROI policy` | 舊檔案沒有記錄量測幾何 | 重建；現行重建器會拒絕產生沒有幾何戳記的基準 |
| `color decision tuning 不一致` 或 `未記錄完整 resolved color decision tuning` | 驗證時與執行期的 `color_decision_tuning` 不同 | 對齊工位設定，或以現行 tuning 重建基準 |
| `顏色模型缺少必要統計量 <欄位>` 或 `顏色模型無法讀取` | 檔案存在但顏色檢查器無法載入 | 確認該基準／方案的重建是否真的完成；殘缺檔案應重建 |

三道門都問同一組問題：**演算法標籤**、**`color_roi_policy`**、**完整的
`color_decision_tuning`**。標籤只說明用哪套規則量的，不說明是在什麼幾何與什麼
參數下量的，而執行期三者都比對，任何一項不符就拒絕載入。因此驗收畫面（挑選）、
發布閘門（放行）與產線（載入）現在問的是同一件事 —— 以前只有產線問到幾何與
tuning，所以一份基準可以在這裡被選中、通過驗收、然後被產線拒絕。

判定依據是顏色模型檔案自己記錄的 `recalibration` 區塊，而不是候選清單登記的
標籤：兩者可能不一致（曾出現統計量從未被改寫、卻掛著現行演算法標籤的候選），
所以兩者都會檢查。這同時適用於`完整顏色基準`候選與`完整顏色方案`套件 —— 套件
打包會複製統計量，但不會複製這些統計量所依附的量測條件，只擋候選、不擋套件
等於留下一道同樣會導致錯誤結論的旁門。

被撤銷（revoked）的逐色修訂不會列出，因為撤銷本身就是操作員的明確動作。
不屬於本工位的項目也不會列出。

系統會在勾選之前就驗證顏色模型能否載入。這一點很重要：無法載入的顏色模型若
被排進矩陣，每一張照片都會變成 ERROR，而且要等整批推論跑完才會發現。

測試期間：

- 不修改目前正式權重；
- 不修改 Active 顏色修訂；
- 不寫入正式檢測結果；
- 不改動人工真值；
- 每列結果保存元件 ID、checksum、延遲、錯誤與變更案例。

完成後可選取一列並按`建立檢測發布版本`。這只建立 immutable 候選，
正式套用仍須回到`工程設定 > 檢測評估版本`處理。

不可發布的組合會被拒絕，包含兩種情況：組合本身失敗（`狀態`欄顯示錯誤訊息），
或該組合有任何一張照片為 ERROR、或完全沒有已判定的樣本。後者要特別注意：
逐張推論失敗時，`狀態`欄仍顯示`完成`，錯誤只反映在`錯誤`欄的張數上——因此請以
`錯誤`欄為準，不要只看`狀態`欄。

### 3.4 驗收既有候選版本

若候選組合已在工程頁建立，進入`工程設定 > 檢測評估版本 > 組合驗收`，
選取狀態為`DRAFT`的版本後按`驗收選取版本`。視窗會鎖定該版本綁定的：

- 模型權重與 config 快照；
- 完整顏色基準；
- 逐色校正修訂。

本流程固定只執行一個組合，不讀取執行當下的 Active 顏色版本。完成後輸入
驗收人員與說明，系統會新增含報告 SHA-256 與組合 ID 的不可變驗收證明，
並讓同一個版本由`DRAFT`顯示為`TESTED`；不會另建下一個版本，也不會覆寫
原始候選檔案。目前 Fusion 組合須使用完整驗收工具，避免單模型矩陣漏綁
另一套模型。

## 4. 指標解讀

結果表格分成「整體判定」與「只歸因於顏色」兩組指標。每一格都以
`張數（比率）`呈現，括號內是該格自己的比率，不可跨欄相除：

| 欄位 | 中文意義 | 分子／分母 |
| --- | --- | --- |
| 準確率 | 正確 OK 與正確 NG 占已決定樣本比例 | `(TP + TN) / 全部已決定` |
| 誤殺（整體） | 實物 OK，系統判 NG（含所有原因） | `FP / 真實 OK 張數` |
| 漏檢（整體） | 實物 NG，系統判 OK | `FN / 真實 NG 張數` |
| 顏色誤殺 | 上列誤殺中原因含 `COLOR_MISMATCH` 或顏色檢查 FAIL 者 | `顏色 FP / 真實 OK 張數` |
| 顏色逃逸 | 真實顏色 NG 被顏色規則放行 | `顏色 FN / 人工標記顏色 NG 張數` |

顏色誤殺是整體誤殺的子集合，必定 `≤ 整體誤殺`；兩者分母相同但分子不同，
因此用整體誤殺去除以任何分母都不會等於顏色誤殺率。驗收工具主視窗下方
統計列顯示的是整體誤殺率，與表格的整體欄位一致。

`相較首組變動`是與第一組（基準組）判定不同的張數；第一列本身顯示
`基準組`，避免和「與基準組完全相同」的 0 混淆。

`錯誤`欄是推論失敗的張數，不計入上述任何統計。當它等於樣本總數時，該組合等於
沒有任何判定：此時準確率與各比率都顯示 UNKNOWN，該組合也不能發布。

主視窗統計列若出現`真值異常 N`，表示有 N 筆標記為已確認、但真值欄不是 OK／NG
的資料列。這種列是損壞的證據：它不列入已確認數，也不列入任何比率的分母，且會
阻擋建立正式快照。正常操作不會產生這種列（確認時強制 OK／NG），出現時通常來自
手動編輯 CSV 或還原了舊格式備份，需逐筆修正。

若驗收集沒有人工標為 `COLOR_MISMATCH` 的真實 NG，顏色逃逸顯示
`UNKNOWN（無真顏色 NG）`。這代表沒有驗證能力，不代表逃逸率為 0%。同理，
沒有可用真值樣本時顯示 `UNKNOWN（無可用真 OK／NG 樣本）`，不是 0 張。

Gate 預設採 fail-closed：

- 快照被修改、影像 checksum 不符或推論錯誤會留下失敗證據；
- 已確認張數不足、仍有未確認照片、漏檢或退步超標會阻擋完整上線；
- 無顏色 NG 真值時，候選不得宣稱顏色逃逸已驗證。

## 5. 重建完整顏色基準

在`工程設定 > 檢測評估版本 > 候選組合`按`重建完整顏色基準`。系統只使用：

- 人工確認為 OK 的完整驗收圖片；
- 指定 YOLO 版本的實際元件框；
- 推論處理後影像座標所對應的元件 crop；
- 該工位 `expected_items` 所列的色別證據（重複的位置會收斂為一次；`LED` 這類
  通用檢測類別不是顏色，不列入）。

每色預設至少 30 個 crop，且至少保留 5 個 holdout crop。系統以 robust
HSV/Lab 統計重建各色中心，並比較舊基準與新基準的 holdout 正確率及中心
漂移。輸出為不可變候選，不會直接修改模型 `config.yaml` 或 Active 指標。

狀態：

- `READY`：證據與安全檢查完整；
- `REVIEW_REQUIRED`：可供矩陣測試，但漂移或其他警告需人工審查；
- `INCOMPLETE`：資料不足，不得組成可用方案；
- `INCOMPATIBLE`：舊演算法或契約不相容，只保留稽核，不再供選擇，且不得發布。

完整顏色基準可再疊加逐色修訂，形成一個不可變`顏色方案`。例如以五色
新基準搭配 Black 的獨立門檻版本；方案會鎖定兩者，切換時不會漏掉其中一項。

### 5.1 發布時的演算法檢查

發布是唯一會影響產線的一道門，因此它獨立檢查一次，而不是信任驗收選單已經擋過：
驗收選單只能讓一份基準不再進入**未來**的比較，而磁碟上既有的驗收報告是在舊演算法
時代寫成的，仍然指名它當時比較過的 artifact。

判定順序是「報告記錄的演算法優先，artifact 自己記錄的為備援」。優先採用報告的
記錄，是因為 artifact 可能在驗收之後被原地重建；當時實際量測的是報告寫下的那一版。
備援讀 artifact，是為了讓早於這個欄位存在的舊報告仍然會被判斷，而不是被放行。

兩者都沒有記錄時視為無法確認，一律拒絕發布。此時的處理方式是：以現行演算法重新
執行顏色基準重建，再用同一批驗收照片重跑驗收矩陣，然後才發布。

### 5.1.1 重建的取樣幾何來自站點設定

顏色基準重建的裁切幾何（`color_roi_policy`）讀自**線上站點模型設定**
`models/<產品>/<區域>/<類型>/config.yaml`，不是模型版本 config 快照。

版本快照決定的是**偵測**：元件框必須來自受測的那個模型版本。但它不能決定顏色的
取樣幾何 —— 快照凍結在模型版本上，而 `color_roi_policy` 是站點本地欄位（模型部署
只保留、不覆寫它），所以沒有任何快照記錄過它。從快照讀會在每個模型版本上都解析成
「不內縮」的預設值，於是重建改用整個偵測框取樣，正是這個 policy 要避開的幾何。

這種錯誤不會有任何徵兆：產出的每一個統計量都格式正確，只是量在別的地方。因此站點
設定不存在時一律拒絕重建，不套用預設值。重建報告會記錄
`color_roi_policy_source`，指出幾何實際來自哪個檔案。

### 5.1.2 沿用舊統計的候選不能借用現行標籤

重建若「沿用」某個顏色（證據不足或安全檢查否決），該色的數字是從舊基準複製來的。
這時候候選是混合體：檔案誠實記錄了這次重建用的是現行演算法，但部分統計量是舊基準
的幾何量出來的。只看演算法標籤，就會讓舊幾何借到它沒有掙到的標籤。

實際發生過：一次重建五色全部被安全檢查否決，產出的 `summary` 與已部署基準**逐位
元相同**，卻標記為 `stats-robust-v4` / `READY`，可以通過全部三道閘門。

現在的規則是：候選記錄 `preserved_colors` 與 `base_algorithm`；有沿用的顏色時，
只有當**舊基準本身也是現行演算法**才視為相容。這樣既擋住上述情形，也不會誤擋
「某色證據不足、從同一演算法的基準沿用」這種正常情況。

### 5.1.2.1 重建前先決定要不要一併調整取樣幾何

`color_roi_policy` 綁在基準契約裡，所以**改它就是讓已部署基準失效** —— 必須連帶
重建、重跑驗收、簽核。因此它該在重建前決定，不要重建完才想到，否則要做兩次。

已知待決事項（Cable1/A，量測見
[`../COLOR_DETECTION_WORK_LOG_20260902.md`](../COLOR_DETECTION_WORK_LOG_20260902.md) 第三節）：
線材是斜的，而量測區塊是偵測框正中央的軸對齊矩形，所以每個區塊都含板子背景 ——
以執行期自己的分母計算，彩色只有 67%–73% 落在基準色域內，黑色 57%。彩色的影響是
稀釋分母（降低靈敏度），**黑色則是把判定綁在治具幾何上**，因為它除以的
`coverage_mean` 是「校準當時框裡有多少是黑的」。

用 `燈光控制 → 顏色開線檢查` 可以直接看到每個色別的量測框裡有多少真的是線材
（`命中` 欄與裁切圖上的暗紗）。若決定調整，**先在真實資料上量門檻餘裕再動**，
不要憑感覺調 —— 這個專案已經有兩次「看起來像整理的改動把黑色推過門檻」的紀錄。

### 5.1.3 重建不能新增色別

重建的定義是「以舊基準為基礎更新統計」：每個顏色都會與它的前一版比對中心漂移、
彩度保留與 holdout 退化，證據不足時則沿用舊統計。一個舊基準沒有的色別，這三件事
一件都做不到，因此重建會直接拒絕，訊息會指出缺少哪個色別。

**新增一個色別要兩件事**，順序不能顛倒：

1. **detector 要能輸出這個類別** —— 需重訓並部署含該類別的模型；
2. **要有一份已含該色別統計的基礎基準** —— 這不在重建流程內，重建只能刷新既有色別。

在這兩件事完成之前，**不要把新色別寫進 `expected_items`**。寫進去的後果不是「少檢
一色」：執行期會把「有一個色別無法評分」折進每一個元件的判定，於是整片板子的每個
檢測都判 FAIL，而且會一直 FAIL。啟動時的 config 驗證現在會擋下這種設定並指名該
色別，但那是最後一道保險，不是工作流程。拼錯字也算 —— `Blakc` 和一個不存在的顏色
沒有差別。

### 5.2 執行期的演算法檢查

站點設定 `color_baseline_algorithm_enforcement` 決定線上載入顏色基準時如何處理
不相容：

| 值 | 行為 |
| --- | --- |
| `warn`（預設） | 記錄警告後照常載入 |
| `strict` | 拒絕載入，並讓該次載入失敗 |

預設是 `warn`，因為單靠一次程式更新不應該有能力停線 —— 站點需要先部署一份由
現行演算法重建的基準。**部署完成後，簽核者應把此設定改為 `strict`**，否則不相容
的配對仍會持續生效。無法辨識的值會解讀為 `strict`：這個鍵在沒有人設定時是不存在
的，所以任何寫在這裡的值都代表「要打開檢查」，把打錯字當成 `warn` 等於給出與
設定意圖相反的結果。

### 5.3 契約版本變更後，每個工位都要重建一次

演算法版本（`recalibration.algorithm`）遞增時，**舊版本的所有基準一律不相容**，
包括已簽核、已部署、正在線上跑的那一份。這是刻意的：版本會遞增，正是因為統計量
的量測方式改了，舊數字與新程式不可比。

`warn` 的站台不會停線，但會**持續用不相符的基準評分**，而且只留一行 log。所以升版
不是「部署完就結束」，每個工位都必須依序完成：

1. 依第 5 節重建完整顏色基準（GUI，具名操作）；
2. 用同一批驗收照片重跑驗收矩陣（第 3.2 節）；
3. 發布並啟用該組合（第 6 節）；
4. 把 `color_baseline_algorithm_enforcement` 設為 `strict`。

第 4 步之前，這個工位並未受到保護。若要一次確認全部工位的狀態，看每個工位
`color_stats.json` 的 `recalibration.algorithm` 是否等於現行版本。

## 6. 啟用與回滾

`工程設定 > 檢測評估版本`分成：

1. `模型與顏色版本`：瀏覽及篩選 YOLO、Anomalib、顏色基準與顏色方案；
2. `候選組合`：自由選擇相容元件並建立 DRAFT；
3. `組合驗收`：快速驗收選取 DRAFT，或開啟完整驗收工具比較多組版本；
4. `上線與回退`：啟用候選或退回前一完整組合。

切換前必須停止檢測。啟用模式：

- `完整上線`：只有無驗證警告的 TESTED 組合可用；
- `限定試用`：保留驗證限制，供監督式試跑；
- `風險接受`：具名記錄人員與原因後套用未完整驗證的組合；
- `BLOCKED`：任何模式皆不可啟用。

回滾同樣以完整組合為單位，不個別改回某個 YOLO 或顏色檔。建立時間以
ISO 8601 UTC 保存，畫面轉換成機台當地時間顯示。
